# Auth, database and the admin panel

Deep dive referenced from `AGENTS.md`. Read this before touching `src/lib/auth.ts`, `src/lib/db/`, `src/proxy.ts`
or anything under `src/lib/admin/`. Changing auth or the proxy needs a maintainer's go ahead first.

Better Auth over Drizzle over Postgres, email and password plus Google. Local development runs against a Postgres
17 of your own on 5432, named by `DATABASE_URL`.

## Schema

- **Two schema files, one client.** `src/lib/db/schema.ts` belongs to the Better Auth CLI. Everything PapSee owns
  lives in `src/lib/db/pap-schema.ts`, which imports `user` for its foreign keys, and `src/lib/db/index.ts`
  composes both. `drizzle.config.ts` lists both paths, so a table added to only one of them silently never reaches
  a migration. `bytea` has no drizzle column of its own and comes from `customType` there.
- **Never hand write the auth tables.** `src/lib/db/schema.ts` is generated by `npx auth@latest generate`. Change
  `src/lib/auth.ts`, regenerate, then `pnpm db:generate && pnpm db:migrate`. The file is Prettier ignored because
  the CLI owns its formatting. The CLI package is `auth`; the old `@better-auth/cli` is stranded on an older
  version.
- **The adapter lives in `@better-auth/drizzle-adapter`**, not in a `better-auth/adapters/*` subpath.
- Deleting a user cascades to `session` and `account`, and now to `patient_profile`, `pap_import`, `pap_day`,
  `pap_event`, `pap_file` and `two_factor` as well, which is what the GDPR and KVKK delete path will need.
  `banned_ip.banned_by` is the one reference that does **not** cascade: a ban has to outlive the admin who placed
  it.

## Plugins and sessions

- **`nextCookies()` must stay last** in the plugin array, and **`admin()` must stay first**. TypeScript keeps the
  plugins array a tuple only while its leading entries are fixed, so a conditional spread in front of a plugin
  erases the field types its schema adds: put `admin()` after the `captcha` and `twoFactor` spreads and `role` and
  `impersonatedBy` silently vanish from the inferred session, which is a compile error at every call site and a
  cast waiting to be written. Verified against this version; check it again before reordering.
- **The proxy guard is optimistic, on purpose.** `src/proxy.ts` uses `getSessionCookie`, which only parses a
  cookie and never touches the database, so it costs nothing per request. It is not a security boundary. The share
  cookie opens the same gate on **presence alone**, because the token behind it is checked against the database in
  `getPanelContext()` and a stray cookie therefore buys nothing but a bounce one page later. The demo cookie is
  the exception that is read by value: there is no later check to fall back on for that one.
- **The proxy protects two prefixes, and the therapy cookies open only one.** `/panel` and `/admin`, matched by
  segment so `/administration` stays public. Demo and share are credentials for reading therapy data and neither
  says who the reader is, so they never open `/admin`; `proxy.test.ts` pins both refusals.
- **The real check belongs in the page.** `getSession()` from `src/lib/session.ts` is the cached server side read.
  Next.js is explicit that a layout is the wrong place for an auth check, because layouts do not re-render on
  navigation and do not stop nested segments from rendering. A layout may read the session to display it, as
  `panel/layout.tsx` does for the user menu, but the redirect lives in the page.
- **A signed in reader never sees the auth pages.** `requireSignedOut()` in `src/lib/session.ts` sends them to
  `/panel`, and it lives in the sign in and sign up pages for the reason above. Demo mode is not a session, so a
  reader looking at the example patient can still reach both.

## Sign up, verification and the code step

- **Sign up is captcha gated, sign in is not.** `src/lib/auth.ts` adds the Better Auth `captcha` plugin scoped to
  `/sign-up/email` with `expectedAction: 'sign-up'`, and only when `TURNSTILE_SECRET_KEY` and
  `NEXT_PUBLIC_TURNSTILE_SITE_KEY` are both set, the same way `isGoogleEnabled` gates Google. Half a pair
  therefore leaves sign up unprotected rather than broken. The token travels in the `x-captcha-response` header,
  which is the only name the plugin reads. The action is checked because both widgets share one site key, so
  without it a token minted for the contact form would be redeemable at sign up. That check also rules out
  Cloudflare's testing keys: their siteverify response carries no `action` at all.
- **SMTP gates address confirmation and the new browser code together.** `parseSmtpEnvironment` decides whether
  `requireEmailVerification`, the `emailVerification` block, the `twoFactor` plugin and the enrolment hooks exist
  at all, the same way `isGoogleEnabled` gates Google, because a self hosted instance without a mailbox could
  otherwise never register anyone. Arming one half without the other is a bug.
- **Better Auth has no mandatory two factor mode.** `user.twoFactorEnabled` is `input: false` and
  `/two-factor/enable` wants a live session and the password, neither of which exists at sign up, so
  `databaseHooks.user.create` arms the flag and `two-factor-enrolment.ts` writes the `two_factor` row. That row is
  load bearing: `/two-factor/verify-otp` refuses a sign in without one, and it holds the lockout counters. Its
  `backupCodes` is a literal `[]` under `storeBackupCodes: 'plain'` because an encrypted empty string makes the
  public `/two-factor/verify-backup-code` answer 500 instead of refusing.
- **The plugin's hook matches `/sign-in/email` only**, so Google sign in has no code step and is not meant to.
- **`/sign-up/email` answers a duplicate address with a generic success** once verification is on, rather than
  `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL`. That is Better Auth protecting against enumeration, and it is why sign
  up ends on a confirmation card and why `errorEmailTaken` no longer fires there.
- **Account mail takes its language from `AUTH_LOCALE_HEADER`.** Better Auth's callbacks run under `/api/auth`,
  outside `[locale]`, where next-intl always resolves the default locale, and `NEXT_LOCALE` is not a fallback: it
  is only written when the cookie is stale or disagrees with `Accept-Language`. A new call that sends mail has to
  send the header too.

## The admin panel

`/admin` answers operational questions about accounts, and it is the one part of PapSee that reads across users.
It shows how many accounts exist, which of them have uploaded and how much, and it can suspend an account or block
an address. Nothing in the product links to it, and `requireAdmin` sends anyone else to the panel.

```text
GET    /api/admin/ip-bans        the blocked addresses
POST   /api/admin/ip-bans        block one, and sign out every session already on it
DELETE /api/admin/ip-bans/[id]   lift a block
```

Those three are the whole admin API. Everything else an admin does is already served by Better Auth under
`/api/auth/admin/*`, and every admin **read** is a server component calling `src/lib/admin/repository.ts`
directly, so there is no admin read API to leak. These three answer `403 forbidden` to anyone `getAdminSession()`
refuses.

- **`user.role` is the whole identity check.** `isAdminRole` in `src/lib/admin/roles.ts` splits on commas and
  compares exact segments, because `setRole` with an array stores `"admin,user"` and equality would lock that
  person out. `adminUserIds` is deliberately unused: `hasPermission` returns true unconditionally for an id in
  that list, which would put an escape hatch around every permission check. The first admin comes from
  `pnpm db:promote-admin someone@example.com`; after that it is the panel. A NULL role already reads as `user`, so
  there is no backfill migration and none is needed.
- **`getAdminSession()` refuses an impersonating session**, whatever role it reports. Admin rights are never
  exercised through a session minted for somebody else, and `roles.ts` is separate from `access.ts` for a reason
  that bites immediately: `access.ts` reaches `getSession` and therefore the database, so a client component
  importing a role constant from it drags `pg` into the browser bundle.
- **Reads come from `src/lib/admin/repository.ts`. Writes on a user go through `/api/auth/admin/*`.** The plugin
  already does the permission check, refuses a self ban, deletes the sessions on ban and auto unbans an expired
  one. Better Auth's own `GET /admin/list-users` is not used: it swallows a failed query into
  `{ users: [], total: 0 }`, which is the same "a broken thing must not look like an empty thing" rule the card
  detection follows.
- **The admin panel never reads therapy data.** `src/lib/admin/repository.ts` selects counts, account columns and
  timestamps and never names a payload column; the profile comes from the existing `getProfile`, whose projection
  is already exactly the six onboarding fields. `pap_day` is counted, never dated, because which nights somebody
  was on treatment is a fact about their health. `repository.test.ts` pins all of that against the source, which
  is coarse but is the only place the rule can be checked without a database. **An admin's only path to a night is
  impersonation**, which is why that has a typed confirmation and a banner.
- **The impersonation banner takes its flag from the server, and must not copy `useDemoMode`.** `/admin` and
  `/panel` are sibling segments, so entering remounts the panel layout and stopping unmounts it, navigating inside
  `/panel` keeps a banner that is still true, and an expired impersonation session redirects to sign in. No
  reachable state leaves it stale, so there is no cookie to read back here.
- **An IP ban is checked in `hooks.before`, on the auth entry paths only.** `src/lib/ip-ban.ts` is that list, and
  it includes the social callback because that is where the session is actually minted. The address is resolved
  with Better Auth's own `getIp` on both sides, so what a ban stores and what a sign in is measured against agree
  by construction rather than by two formulas matching; `POST /api/admin/ip-bans` therefore validates with
  `net.isIP` and then round trips the typed value through `getIp`. Two consequences follow from that resolution
  and neither is obvious: **`getIp` masks every IPv6 address to its /64**, so an IPv6 ban is a subnet ban, and
  **it answers `127.0.0.1` in development and test**, so banning that address locks out every local sign in
  including your own. Blocking an address also deletes every session already on it, because refusing the next sign
  in is only half a ban.
